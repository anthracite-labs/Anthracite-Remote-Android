# Full-repository audit — remediation record

Audit target: PR #8 head `1dad773`. Everything below is at `be88d27` and later.
Each finding is marked **fixed**, **partly fixed**, or **open**, with the test that
covers it or the reason it is not closed. Nothing here is claimed as verified on a
real host, device, cluster or GitHub installation.

## Critical

| ID | Status | Change and evidence |

| C-01 iOS hand-written keyscan spoke an invalid KEX | **fixed** | The scanner no longer implements SSH. `HostKeyScanner` runs a real `NIOSSHHandler` handshake and stops at the host-key delegate: the delegate records the parsed key and then *fails* the validation promise, so no credential is ever offered. | P0-1 the environment-file guard never matched | **fixed** | `DeployPlans.envFileCommand()` compared a ten-character `ls -ld` mode string with the eleven-character pattern `d????------`, which cannot match. Every container deployment with environment variables exited 73 before starting a container. Replaced with `stat`-based checks (GNU `-c`, BSD `-f` fallback): the directory must not be a link, must exist, must be owned by the connecting user and must be exactly 0700; an existing target is refused without being opened; `set -C` keeps the create exclusive; a write that fails half-way removes its own partial file (new exit 74); after writing, the file is re-checked as a regular 0600 file. Evidence: `SFTPClientStateTests` drives the real client through a scripted in-memory peer: one INIT for concurrent first callers, silent server, version 4 failing closed, disconnect and an impossible frame, delayed and out-of-order replies, a late reply after a timeout, cancellation, `close()` with a request in flight, an upload/download round trip and a refused write leaving no temporary file. **Not proven:** a live `sftp-server`. |

## Final safety pass — 2026-10-23 (third assignment)

Review base `021bbeb`. Both defects were reproduced before anything changed, and
the reproductions are the tests that now pass.

| ID | Status | Change and evidence |
| --- | --- | --- |
| A1 cleanup could delete a competing process's file | **fixed** | The write step made the destination an exclusive create, but its failure handler removed `$f` whatever had caused the failure, so a file created by a competing process between the existence check and the create was deleted by this app. Reproduced under dash and bash (both exited 74 and the competing file was gone). Ownership is now established before anything can be removed: each operation claims `~/.anthracite/deploy/<name>-<token>` with `mkdir`, which is atomic and fails when the name is taken, and writes the values only inside it. A won `mkdir` is the proof of ownership; a lost one means the name is held by somebody else, so nothing is written and nothing is removed. Removal is confined to the claimed directory and `rmdir` refuses to remove it while anything else is in it. Exit 73 = the claim or a check failed, 74 = a write failed inside a directory this operation owns and cleaned up. **Why `mkdir` and not `exec 3>"$f"`:** POSIX makes a failed redirection on `exec` (and on the special builtin `:`) terminate a non-interactive shell, so dash exits with status 2 instead of reporting "not mine" — verified; `mkdir` fails as an ordinary command in dash, bash and busybox ash. Evidence: `DeployEnvFileShellTest`, which executes the generated command in a disposable HOME under every shell present (`/bin/sh`, dash, bash), with the race made deterministic by a barrier at the validation→claim boundary: the competing file survives with its content and mode, a lost claim leaves the directory otherwise untouched, a partial write after a won claim is removed (exit 74, nothing left behind), an operation killed mid-write never touches another operation's file, a stale leftover is not deleted by a different operation, and cleanup beside a foreign file removes only this operation's file. |
| A2 cancellation during the initial SFTP handshake | **fixed** | Cancelling a caller 150 ms into a silent handshake returned after **29.92 s** with `timedOut` and had closed the channel: `start()` awaited the shared handshake with `Task.value`, which ignores the awaiter's cancellation, and the caller that started the handshake also owned its terminal transition. The handshake now has its own waiter list under the same exactly-once rule as requests — each waiter is removed before it is resumed by whichever of success, connection failure, `close()` or that caller's cancellation arrives first — and the shared task owns the terminal state. Cancellation is prompt and local: it cannot close another caller's channel, start a second INIT, or revive a dead connection. Evidence: `SFTPClientStateTests` — prompt `CancellationError` with one INIT and no close; a later call after the cancellation gets the shared handshake's own timeout and then a terminal failure; one of two callers cancelling still lets the other receive its own result with the channel open. |
| A3 managed-resource invariants | **unchanged, re-verified** | No production change was made in these areas; the suites that pin them ran green at the final commit: Kubernetes create-only and `can-i create` (`DeployGuardTest`), the server-enforced delete precondition (`DeployGuardTest`, `DeployKubernetesDeleteShellTest`), rollback still narrowed-not-closed (plan warning + `DeployGuardTest`), container identity (`DeployContainerIdentityTest`), host-key checking (`SshSessionTest`, `HostKeyConversionTests`), approved-key pinning and tmux identity (`TmuxPresenceTests`, `ProtocolTests`), provisioning and cancellation (`ProvisionJobsTest`, `ProvisionPlannerTest`), terminal keys/writer/emulator (`TerminalKeysTest`, `TerminalWriterTest`, `TerminalEmulatorTest`, `TerminalTests`), SFTP limits and EOF (`TransferSafetyTests`, `SFTPClientStateTests`, `SftpBrowserTest`), credential storage (`CredentialCryptoTest`, `SecretStoreTest`, `HostStoreTest`). |

**Residual risks recorded, not fixed:**

* A host command cancelled *in flight* leaves a partial `0600` file inside its own
  `0700` directory. The app only removes a file when the write it sent returned
  success, because after a cancellation it cannot prove ownership — and proving
  nothing is better than deleting something that is not ours. A later operation
  uses a different random name and deliberately leaves that leftover alone.
* A same user who can write inside an operation's brand-new `0700` directory can
  still race the two shell commands inside it. That window is microseconds and
  the name is 64 random bits; nothing outside the directory is ever touched, and
  `rmdir` will not remove the directory while their file is in it.

**Not verified:** any real Linux host, container runtime, Kubernetes API server,
OpenSSH/SFTP server or physical device. Everything above ran in CI against
scripted peers, real POSIX shells on disposable directories, and an in-process
SFTP server.

## Remaining-findings pass — 2026-10-23 (fourth assignment)

Base `1253f39`. Each priority was reproduced before it was changed; the ones that
could not be reproduced are marked as such rather than fixed speculatively.

| ID | Priority | Status | Change and evidence |
| --- | --- | --- | --- |
| R-1 | P1 — iOS SFTP handshake completion race | **fixed** | Reproduced first: `handshakeSucceeded()` released every waiter even when the state was already `.failed`, and a request could register after death and burn its own timeout. The reproduction was run red — `Optional(SFTPError.timedOut) is not equal to Optional(SFTPError.notConnected)` on attempts 0–10 — before the fix. Success now releases waiters only from `.starting`; in the failed state it releases them with the **first** terminal cause; request registration resumes immediately with the stored terminal error. Evidence: `SFTPClientStateTests` — 40 attempts of greeting-then-disconnect, a second caller learning the same cause, and a late greeting that cannot resurrect a failed connection. Still: no live `sftp-server`. |
| R-2 | P2 — bound iOS terminal output | **fixed, with the bound described honestly** | `TerminalOutput` is an `AsyncSequence` with a 512 KiB high-water and 128 KiB low-water mark; the collector's handler appends, and the channel is told `autoRead=false`/`true` on its own event loop. No byte is dropped, truncated, reordered or detached, and the stream is not a hard cap: a producer that ignores the stop signal keeps its bytes, which the class documents. The collector's private unbounded `stderrBuffer` — which nothing read — is gone; stderr now goes into the same stream, and the peer's exit status is exposed instead of being stored and ignored. Evidence: `TerminalOutputTests` — peak queue measured over a reader that honours the stop, a blocking producer that loses nothing, ordering across stop/start, UTF-8 and ANSI intact, a parked consumer cancelled, and the real `ShellCollector` driven through an `EmbeddedChannel` (which is also what proved the stop signal is asked for). **Not proven:** a live SSH session, where the window actually closes and the remote program blocks. |
| R-3 | P3 — GitHub pagination | **fixed** | Listings follow `rel="next"` up to 10 pages. A continuation is used only if it is https on `api.github.com` with no user-info and no port; duplicates are dropped by number/id; auth and `X-GitHub-Api-Version` headers are sent on every page; a loop back to a page already read stops the walk. The first implementation returned the first page as a complete listing when the server offered a continuation it would not follow — that is the failure this work exists to remove, so a refusal now raises `incompleteCollection`, as does the page limit. Cancellation stays `CancellationError`, rate limits and 401 surface as themselves. Evidence: `GitHubTests` — multi-page, empty page, five unsafe links, a foreign relation, a loop, the page limit, a later-page rate limit, a later-page 401 and a transport failure. The SHA-pinned merge protection is untouched. **Not proven:** a live API call. |
| R-4 | P4 — persisted managed deployment identity | **fixed for Android** | A record is written at creation only when the runtime or cluster reported an immutable identity (container id, Kubernetes UID), together with the host id, host-key fingerprint, runtime, context, namespace and kind; a native unit has no identity, so none is written. On restore the record is compared with the current target before anything is read — a record from another host, host key, runtime, context or namespace is never used — and the live identity is read before any action is offered. Only an equal identity enables logs and removal; replaced, gone, unreadable and other-target are each shown as themselves. Records are per host, versioned, validated on read and refused whole if anything is invalid; no secret or environment value is stored. Evidence: `ManagedDeploymentsTest` — round trips, a name used as an identity, a missing context, garbage and downgraded records, a failed commit restoring the previous record, per-host slots, and every reconciliation outcome. **Not proven:** a real process death on a device. |
| R-5 | P5 — reproducible iOS builds | **fixed** | `ios/Package.resolved` carries the seven pins the toolchain itself resolved on `macos-15` (swift-nio 2.104.0, swift-nio-ssh 0.15.0, swift-crypto 4.5.2, swift-asn1 1.7.3, swift-atomics 1.3.1, swift-system 1.8.1, swift-collections 1.6.0 — the newest collections release needs a newer tools version than the runner has). Simulator selection still takes the first available iPhone. No security check was weakened. |
| R-6 | P6 — unsafe recursive SFTP deletion | **constrained, guarantee refused** | SFTP v3 has no handle-relative remove, no `openat` and no conditional delete, so the recursion cannot be made atomic and is not described as such. Each directory is re-read with `lstat` immediately before it is descended into; if the entry is no longer the plain directory that was listed, the delete stops rather than following it. The depth and entry caps stay. The confirmation text now says the delete is a series of removals that stops if the folder changes. Evidence: no unit test drives it — `RemoteFiles` needs an SFTP session, and inventing one would not test the protocol behaviour that matters. Recorded as **not covered**. |
| R-7 | P7 — Kubernetes rollback identity safety | **narrowed and verified, not atomic** | The delete keeps its server-enforced UID precondition (`DeleteOptions.preconditions.uid` via `kubectl delete --raw … -f -`).
